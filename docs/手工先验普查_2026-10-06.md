## 一、结论：要先分清「规则族」和「规则实例」

| 口径 | 数量 | 说明 |
|---|---|---|
| **规则族**（可归责的最小单位） | **21 条** | 四部和声 R01–R11（11）+ 简谱/旋律 R01–R10（10）。两套编号体系互相独立，R01 两边含义不同 |
| **规则实例** | **251 条** | 240 条 = 25 个子风格 × 9–10 条；另 11 条 = 众赞歌（顶层，无 subs） |
| 其中阈值可被机器读取（`param`） | **140 条** | 全部在 lead-sheet 侧；由 `learn` 写入，"改 YAML 即改判决" |
| 阈值写在代码里、YAML 不可编辑 | **111 条** | 众赞歌 11 + lead-sheet 侧无 param 的 100 |

**251 这个数是「同一套规则在 25 个子风格里各存一份」的实例计数，对外报数应报 21 族 / 140 活阈值。**

## 三、对论文的直接影响（新发现）

**P1 的核心实验在四部和声分支上做不了。**

论文主张「改 YAML 里存的一条阈值会改变检查器的判决」作为相对 CHORAL 的可证伪差异。但实测：

- 读 `hard_rules[*].param` 的 `_rule_param()` **只存在于 `score_learning/leadsheet/check.py`**；
- `score_learning/grammar/check.py`（众赞歌 / SATB）**完全没有**读 YAML 阈值的代码 ——
  它的 11 条规则的阈值（十二度间距、导音重复、旋律禁用音程等）**写死在 Python 里**。

而论文的 Table 3、Table 4、RQ2 的 `out_of_grammar` 与故障注入、以及盲评包，
**全部走四部和声分支**。也就是说：P1 建议的「编辑 `hard_rules[R04].param`」这个演示
在论文主结果所依赖的那条分支上**无法执行**，只能在 lead-sheet 分支演示。

三条出路，按成本排序：

1. **改口径**（最省）：把贡献 1 收窄为「在习得型 lead-sheet 规则包上（9 个子风格 × 受影响规则），
   改 stored threshold 会改判决，有 `test_hard_rules_live.py` 断言」，并明说四部和声分支尚不可编辑。
2. **给四部和声分支补 param**：把 `grammar/check.py` 的判断阈值提出到 `hard_rules[*].param`，
   众赞歌 YAML 加 11 组阈值 —— 半天到一天，且能把 P1 变成全分支成立，**顺手补上 P10 的逐条消融接口**。
3. 维持现状但在 Limitations 写明。

附带一致性提示：`sacred/chorale/grammar.yaml` 的 `hard_rules` 在**顶层**，
其余 8 个包在 `subs.<子风格>.hard_rules`。任何按 `subs` 递归的工具（含已有的审计脚本）
都会**漏掉众赞歌这 11 条**——本次普查的第一版脚本就踩了这个坑。
