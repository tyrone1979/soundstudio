# 《符号音乐与器乐生成专题调研报告》× 本软件（composerchat / Score Studio）对比分析

> 对照基准：调研报告（截至 2026 年 9 月）第 2–8 章所述的方法家族、模型谱系、功能总表、评测体系与趋势判断。
> 本软件事实以当前代码为准：`compose_kernel.py`（确定性内核）、`llm_compose.py`（LLM 翻译器）、`style_skeleton.py`（风格骨架）、`score_learning/`（风格学习）、`score_studio.py` + `studio_daw.py`（Studio UI）。

---

## 0. 一句话定位

**报告里的系统是「学出来的生成器」，本软件是「写出来的编译器」。**

报告通篇讨论的都是「用什么 token 表示音乐、用什么模型从数据里学出音乐语法」；本软件两者都没有——它**不训练模型、不做 token 化**，而是让 LLM 把自然语言编译成一段**内核脚本调用序列**，再由确定性算法展开成音符。这个根本差异决定了后面所有的对比结论：报告里的系统追求「生成得像训练数据」，本软件追求「生成得在乐理上必然正确、可控、可复现」。

## 1. 表示层：五大家族之外，还有第六条路

报告第 2 章归纳了五种 token 化家族。本软件**不在其中任何一种**，它用的是更高一层的「控制流表示」。

| 维度 | 报告五大家族 | 本软件 |
|---|---|---|
| 表示对象 | 音符序列（音高/时值/力度/位置） | **作曲动作序列**（`new_score` / `set_sections` / `set_harmony` / `accompaniment` / `melody` / `fugue` / `cadence` / `finalize`） |
| 一首 16 小节曲的序列长度 | REMI 数千 token；Octuple ≈ 音符数（数百）；PMT ≈ 4 token/音符 | **约 20–40 个脚本调用**（几十个参数对象） |
| 时间精度 | PMT 10ms 栅格（2.3ms 误差）；REMI 量化到网格（中位 53ms 误差） | **16 分音符栅格**（`DUR_QL` 最小 0.25 拍；120 BPM 下 125ms），**无任何微时值** |
| 多轨/多声部 | REMI+ 加轨 token、MuMIDI 建模轨间依赖、PMT 16 轨 | `new_score(voices=2/3/4)` 显式声部，伴奏自动补内声部 |
| 可解释性 | token 序列人不可读 | **调用序列人可直接读、可手改、可 diff** |
| 可复现 | 靠采样温度，本质随机 | `seed` 参数，**同 seed 逐音符复现** |

**谱系上最接近的三项工作**（报告都提到，但都不是同一条路）：

- **MuseCoco（2023）「文本→音乐属性→符号音乐」两段式** —— 本软件是同一思想，只不过中介层是「脚本调用」而非「属性 JSON」；
- **Text2Score（2026）「先规划小节级结构、再逐节生成」** —— 对应本软件的 `set_sections` → 逐段 `set_harmony/accompaniment/melody`；
- **Amadeus（ACL 2026）「音符自回归 + 全局属性离散扩散」** —— 本软件把全局属性（拍号/速度/调性/曲式）彻底**外置**为显式参数，由人而非模型决定。

**这带来的两个极端后果：**

- ✅ **结构正确性上碾压所有 token 家族。** 报告里没有任何系统能保证「每小节时值一定填满」「终止式一定存在」「外声部一定无平行五度」。本软件把这些做成了**内核硬约束 + 后处理修复**：`validate_score_spec` 校验、`_fix_parallel_outer` 自动规避、`cadence` 忘了调就自动补。这类错误在 token 模型里只能靠数据分布概率性地回避。
- ❌ **分布保真度上无从谈起。** 报告的核心指标 FMD（Fréchet Music Distance）衡量「生成集与参考集的分布距离」——本软件的输出分布由 7 种伴奏织体 × 4 种节奏型 × 4 种 contour 的**模板笛卡尔积**决定，本质是一个小得多的假设空间。而且微时值维度上是**全行业最差的一档**：连 MIDI 文件里都不存在微时值，比 REMI 的 53ms 量化误差还粗（125ms）。报告第 8 章批评「量化网格磨平微时值」，这条对本软件的杀伤力比对任何神经模型都大。

## 2. 模型与训练：三次跃迁 vs 零训练

报告第 3.1 节梳理了三次跃迁（深度序列建模 → 表示工程与预训练 → LLM 范式迁入）。NotaGen 是第三阶段的完形：1.6M ABC 预训练 → 8948 首古典微调 → CLaMP-DPO 强化学习。

**本软件：零参数学习，双引擎分工。**

| 组件 | 角色 | 是否学习 |
|---|---|---|
| `compose_kernel.py` | 确定性作曲内核（含赋格引擎、声部进行修复、织体展开） | ❌ 纯规则/算法 |
| LLM（DeepSeek API） | **只做编译器前端**：自然语言 → 脚本调用序列 | ❌ 不微调、不训练，只 prompt |
| `style_skeleton.py` | 风格包 → 内核调用序列（**完全不经过 LLM**） | ❌ 查表 + 规则 |
| `skills/composition/genre/packs/*/meta.yaml`（26 个） | 风格知识载体 | ⚠️ 由 `score_learning` 从语料**统计**而来，是文本不是权重 |
| `music_score/audio_engine.py` | 加法合成器（7 谐波 + ADSR，自动识别乐器） | ❌ |

**优势**：不需要 GPU；风格包是人可读可改的 YAML（改一行就改一个风格，模型做不到）；生成过程完全可审计；断网时 `/skeleton` 仍能确定性出谱。

**劣势**：**没有从数据中学到「音乐语法」**。想要新风格只能手写包或写新内核脚本，不能靠喂数据变强；没有 RLHF/DPO 这条质量提升通路（NotaGen 靠 CLaMP-DPO 三轮迭代显著提分，本软件没有对应的「奖励信号」概念）；风格包目前**只有 4/26 个真有从语料挖出的 features**（celtic-jig 273 条、chorale 24、celtic-air 14、march 2），其余是手写/模板。

## 5. 专题：古典乐谱（报告第 4 章）—— 本软件唯一领先的方向

报告第 4 章的三条线路（众赞歌与对位线、交响乐线、乐谱文本线）里，本软件落在**第一条线**，而且做得比报告里绝大多数系统更"硬"。

**赋格**：报告里**没有任何一个系统**提供显式的、参数化的赋格构造引擎。NotaGen 是靠 8948 首古典语料**隐式**学到巴赫风格；本软件是算法构造：

```
主题原型库 → 答题（守调/真实）→ 对题（反向级进 + 强拍协和 + 避平行五八度）
→ 主题头模进间插段 → 中部关系调进入 → 密接和应 → 属持续音 + 主和弦终止
```

`new_score(voices=2/3/4)` + `fugue` 脚本，全部确定性、按 seed 复现；`prefs['fugue']='auto'` 使**每首曲子必含赋格段**，即使 LLM 忘了调也会由 `_ensure_fugue_section` 兜底插入。矩阵测试 26 风格包 × 8–32 小节 × 2/3/4 声部 × auto/full ≈ **932/936 零 CRITICAL/MAJOR 问题**。

这是本软件相对报告谱系**最实质的差异化**：它用规则和算法换来了 token 模型需要用大量数据去逼近的「对位正确性」，而且这个正确性是**可验证、可保证**的，不是概率性的。

**但报告第 4.3 节列的三条短板，本软件一条没躲开，且有两条更严重：**

| 报告指出的短板 | 本软件状况 |
|---|---|
| 表情信息缺失（ABC/MIDI 只记音符） | **同样缺失**，且没有任何补表情的通路（报告至少还有 VirtuosoNet 这条补路） |
| 配器细节浅（乐器法、音域、声部平衡外行错误） | **同样浅**（`/orchestrate` 只改编制）；不过内核有音域约束与声部交叉检查，随机性错误更少 |
| 形式创新有限（20 世纪后语汇弱） | **更弱**：26 个风格包全是调性音乐，无无调性/微分音/频谱/序列主义 |

另外报告提到 NotaGen 的里程碑意义在于「从论文到舞台」（钢琴家公开演奏）——这条本软件差得最远，因为第 4 章的隐含前提是**输出足够好听**，而本软件的评测体系根本没有"好听"这个维度（见第 7 节）。

## 6. 专题：纯器乐与 BGM（报告第 5 章）

报告第 5.5 节列的「符号/MIDI 路线 BGM 工具」——Magenta Studio 五件套、BandLab Smart Tools、AIVA——才是本软件的真实同类，而不是 Stable Audio / Suno 那些音频模型。

**与 Magenta Studio 五件套逐项对照：**

| Magenta Studio | 本软件 | 结论 |
|---|---|---|
| Continue（续写旋律/鼓组） | `/extend`、`/continue`、`/develop` | 有，但非音符级 continuation |
| Generate（从零生成） | `/style` + 描述；`/skeleton 风格名`（确定性） | **更强**：确定性骨架可复现，且必带赋格 |
| Interpolate（两 pattern 间渐变） | ❌ 无 | 缺失 |
| Groove（给量化鼓组加微时值人性化） | ❌ 无，且内核设计上就没有微时值 | 缺失 |
| Drumify（给旋律配鼓） | ❌ 无打击乐轨道 | 缺失 |
| 全部本地运行 | ⚠️ 内核本地，LLM 需 API | 半满足 |

**与 AIVA 对照**：AIVA 卖点是「导出真实 MIDI 进 DAW 编辑 + 250+ 风格预设 + 可上传参考训练自有风格模型 + Pro 档版权转让」。本软件的 26 个风格包对应其 250+ 预设（数量少一个量级，但每个包是**可编辑的知识文件**而非黑盒预设）；`/learn-score` 对应其"上传参考学风格"（本软件的语料只有 10 首，学出来的东西有限）；**DAW 内编辑这一项 AIVA 有而本软件没有**。

**音频渲染是这条线上最大的观感差距**：报告第 5.2 节的模型产出的是真实乐器音色的音频；本软件的 `audio_engine.py` 是 7 谐波加法合成 + ADSR。作为"检查草稿"够用，作为"交付成品"远不够。报告第 8 章预言「符号模型会越来越多地内置高质量渲染器」——本软件正处于这条预言的起点，且已具备 FluidSynth + GeneralUser-GS.sf2 的接入痕迹（见 `play_midi.py`），换用采样合成是一步可做的事。

## 7. 评测体系：规则校验 vs 分布距离（报告第 7 章）

报告第 7.2 节说评测正在收敛为「FMD（分布保真）+ 属性遵循度（速度/调性/流派命中率）+ 人评（音乐性）」三件套。

本软件走的是**完全正交的一条路——规则校验**，两者甚至连要回答的问题都不同：

| | 报告三件套 | 本软件 |
|---|---|---|
| 问的问题 | 生成集分布离真实音乐多远？提示词要求满足了多少？人觉得好听吗？ | 这份乐谱在乐理上有没有错？ |
| 具体手段 | FMD、速度/调性命中率、盲听 A/B | `validate_score_spec`（内核级：小节填满、声部齐全、和声合法）+ `analyze_composition` 7 类（调号一致性 / 节奏完整性 / 平行五八度 / 声部交叉 / 音域 / 旋律进行 / 终止式） |
| 输出形态 | 一个分数 | **可定位的问题列表**（"声部 2 第 7 小节时值 = 3 拍，应为 4 拍"） |
| 能否自动修 | 不能（只能重训/重采样） | **能**：平行五度自动规避、终止式自动补、`skeleton_spec(tries=8)` 按问题数挑最优 seed |

**强项**：报告三件套给不出"第几小节第几拍错了"，本软件给得出；而且它能**自动修**。这是确定性内核独有的能力，FMD 类指标永远做不到。

**弱项（三条都缺）**：
1. **没有分布保真度度量** —— 无法回答"像不像肖邦"；
2. **没有属性遵循度打分** —— 但这是因为**遵循是硬保证**（`/tempo 72` 一定 72），无需打分；这一点反而是本软件相对报告"属性遵循度普遍只有 0.57（调性）"的优势；
3. **没有音乐性/人评通道** —— 也就**没有防抄袭检查**（无最近邻距离）。

一个有意思的对照：报告的"元发现"是「没有任何现有系统能同时做到高提示词遵循与高分布保真」（Amadeus 靠堆叠织体换遵循度、PMT 遵循度落后）。**本软件是这条权衡曲线外的第三种选择：彻底放弃分布保真，换取 100% 的结构与属性遵循。** 这也解释了为什么它听起来可能不如 MusicGen"像音乐"，但每一份输出都能通过乐理检查。

## 8. 局限与趋势（报告第 8 章）逐条对照

| 报告判断 | 对本软件的判定 |
|---|---|
| 表示之争转向「时间均匀性」与「微时值保真」 | **本软件是反方向**：既不时间均匀（事件式脚本）、也毫无微时值。若认可这个趋势，本软件需要补一层"演奏渲染"（velocity 曲线 + rubato + 踏板）才能对齐 |
| 符号-音频桥是下一个价值高地（符号做结构、音频做音色） | **本软件正好站在桥的符号这一侧**，且结构侧极强；缺的是桥本身——已有 FluidSynth 痕迹，接上是低垂果实 |
| 商业化上符号路线被低估，付费流向「授权清晰 + 可编辑」 | **授权清晰：满分**（无训练数据）；**可编辑：不及格**（软件内不能改音符，只能导出后改） |
| 古典乐谱下一站是「演奏闭环」（作曲→配器→表情演绎→高保真渲染） | 本软件完成了第 1 步的前半（作曲：确定性 + 赋格），第 1 步后半（配器）很浅，**第 2–4 步全无** |
| 评测碎片化 | 本软件**绕开了**这个问题（改用规则校验），代价是无法回答"好不好听" |

## 9. 本软件独有的、报告里找不到的东西

反过来看，报告的系统也做不到的几件事（这些是本软件的存在理由）：

1. **可保证的正确性** —— 不是"大概率不出错"，是"内核不允许出错"（时值必满、终止式必有、平行五度自动修）。
2. **逐音符可复现** —— `seed` 参数使同一提示词可精确复现某一版；token 模型只能靠固定随机种子碰运气，且换模型就失效。
3. **确定性赋格引擎** —— 报告全篇无对应物。
4. **风格知识是人可编辑的文本**（26 个 `meta.yaml`）而非权重 —— 想让"圆舞曲"少用七和弦，改一行 YAML 即可；模型需要重训。
5. **不依赖训练数据** —— 语料 10 首也能出谱；数据规模不再是瓶颈，瓶颈是规则与模板的丰富度。
6. **完全可审计的生成过程** —— 每个音符都能追溯到"哪个脚本调用、按什么规则产生的"；这是确权与专业工作流里最被低估的一项。

## 结论

本软件与报告里的产品**不在同一条赛道上竞争，而是互补**：

- 报告的系统解决「**如何让机器产出听起来像音乐的东西**」——它们在音频质量、风格多样性、微时值真实感上全面领先，且随数据规模单调变强；
- 本软件解决「**如何让机器产出一份在乐理上必然正确、可控、可复现、可审计的乐谱**」——它在结构正确性、属性遵循度、可解释性、确权清晰度上领先，且不依赖数据规模。

最贴切的行业类比是：报告里的系统是**"神经网络作曲家"**，本软件是**"带 AI 前端的计算机辅助作曲（CAAC）内核"**——更接近 DeepBach/Coconet 那一脉的现代化身，而不是 NotaGen/MusicGen 那一脉。

**因此最值得做的下一步不是"补模型"，而是把符号侧的优势延长到报告的"演奏闭环"**：先加表情渲染层（P0），再接高质量音色（P1），本软件就能从"能生成正确乐谱"升级为"能生成正确且有演奏感的乐谱"——这恰好是报告判定为"下一站"的位置，且这条路上没有训练成本。
